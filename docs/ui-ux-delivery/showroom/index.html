Why it exists

Why quick interface work so often fails review

The same four problems turn up whenever interface work moves quickly between people, tools and agents. Each one has a small, repeatable answer in the kit.

  • It looks finished before anyone tries it

    The happy path renders, but the error, empty and disabled states were never built, and nobody noticed because the screenshot looked right.

    The kitEach component lists its states up front, and each state gets a check that can be run again.

  • Keyboard users get stuck

    A control nobody tabbed to cannot be reached, or focus disappears inside a dialog and never comes back.

    The kitKeyboard paths and focus return are written into the acceptance criteria and checked in a real browser.

  • One screenshot stands in for testing

    A single image of one state at one width becomes the proof that a whole component works on every device.

    The kitChecks run at agreed widths and save their results as evidence, and every check is first shown to fail.

  • Passing checks get mistaken for approval

    Decisions are lost between tools and agents, and a green test run quietly replaces the judgment of the person who owns the design.

    The kitEvery review records who or what performed it, so automated results and human decisions are never confused.

How it works

Five stages, each with a template and a clear output

Use the arrow keys to move between stages. Each stage produces something a reviewer can open, not a promise that it was done.

Write down what you are building before you build it

Record the audience, their main task, the real content, the stack, the browsers and assistive technology you support, and who owns each decision. If a site already exists, capture its version and the qualities worth keeping before anything is rebuilt.

Open the project brief template

What a reviewer gets

  • One brief every tool and agent works from
  • The supported devices that decide which checks are required
  • References with reuse rights recorded

Keep one source for every token

Colours, type, spacing and focus rules live in one place, with contrast ratios checked and each value marked approved or provisional. The visual direction becomes criteria a reviewer can actually check.

Open the design system template

What a reviewer gets

  • A token source with its version
  • Approved and prohibited colour pairs
  • Visual acceptance criteria

Build only what the screens need, with every state

Components are built in the stack that will ship. States are part of the component, so default, error, empty, disabled and loading are written as stories or fixtures and checked, not assumed.

Open the component spec template

What a reviewer gets

  • Stories or fixtures for each state
  • Keyboard and accessibility checks that can fail
  • Acceptance written as action and result

Assemble real screens at real widths

Components are judged together, with matching real content and states at the agreed widths, because a component that works alone can still fail inside a crowded screen.

Open the screen spec template

What a reviewer gets

  • Screens at each agreed width
  • Focus order and landmarks recorded
  • The critical flow and its expected outcome

Hand over evidence, not a feeling

Compare the existing version and the candidate on the same screens, content, states and widths. Record which results came from tools and which from people, and say plainly what review remains.

Open the review and handoff template

What a reviewer gets

  • Saved results for every check
  • Who performed each review
  • Known gaps and the next owner

Get started

Start on your own project in three steps

The kit is plain Markdown, CSS and a few test files. It works beside any stack and installs nothing into your site.

  1. Write the brief

    Fill the project brief with your audience, content, stack and supported devices. Every later decision then has something to point back to.

    Project brief template

  2. Swap in your tokens

    Replace the placeholder token file with your own values, exactly as the switch above does, and record which values are approved.

    Placeholder tokens

  3. Run the checks and keep the results

    Choose the static HTML or the React with Storybook route, show each check can fail, then save the passing evidence for review.

    Testing starter
git clone --depth 1 https://github.com/aispanda/Reusable-Delivery
cd Reusable-Delivery/docs/ui-ux-delivery
npm install
npm run check:static
npm run storybook

Questions

Before you adopt it

Do I need React or Storybook?

No. There is a route for static HTML that needs only Node and Playwright in a separate test folder, and other stacks can run the same kinds of checks with their own browser test runner.

Will my project inherit the AI Spanda brand?

No. The examples use neutral placeholder tokens on purpose. Only this page and the README wrapper carry the AI Spanda style.

What does it cost, and what is the license?

It is free under the MIT license. Storybook, Playwright and axe are installed separately and keep their own licenses.

Does it work with AI coding agents?

Yes. The templates are written so an agent can fill them and run the checks, while the design owner keeps the decisions that need judgment. Every review records whether a person or an agent performed it.
