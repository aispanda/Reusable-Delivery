## Review and acceptance

Use the in-app browser, Chrome, or another browser, manually or through Playwright, as the intended end user. Verify the actual page layout, related lists, available actions, and visible data relevant to the journey. Record the entry point, user role, actions, expected behavior and observed result. Use MCP/CLI for backend checks on records, metadata, and supporting state. An inaccessible page or missing action leaves the dependent user journey unverified. Record human acceptance separately from test execution.

Check both human readability and AI execution precision; one reviewer may wear both hats, clearly labeled as maker review when applicable. Human-reader perspective is not human acceptance. A required independent checker must be fresh and inspect actual evidence against frozen criteria. Mockups/model opinions do not prove implementation.

For requested/needed review, send only permitted context: precise question, exact revision, criteria, relevant artifact/evidence, and bounded output structure. Ask for findings with location, impact, correction and verification. Record reviewer, model and reasoning, scope, findings, dispositions and affected rechecks; verify advice before acting. Reuse unchanged valid reviews. Access/model/transmission failures are blockers, not verdicts. Preserve required independent and human acceptance separately; do not invent approval gates or approvals.

For code changes, choose repeatable checks for the changed behavior and its material failure paths. Record the revision, runtime versions and observed results. Verify findings against agreed behavior and reproducible cases. Record confirmed defects and unresolved findings. Send policy questions to the decision owner before changing behavior. Review findings inform decisions. Passing checks require observed results. Where warranted, retain a regression test and rerun affected checks on the repaired revision. Check transaction, access and recovery boundaries touched by the change. Use measurements to support performance claims.

The story coordinator, assigned by the accountable human, uses the agreed criteria, risk and repository rules to decide what to check, when and who checks it. Plan this before implementation and revisit it when scope or risk changes. The accountable human owns acceptance policy, business decisions and any required release approval. For material changes to behavior, shared contracts, access, data or recovery, schedule a fresh independent reviewer after the writer's checks and before merge or handoff. Follow any stricter project requirements. Choose a human or an AI permitted by project policy and suited to the risk and context. Record the selected model and reasoning for an AI review. The reviewer inspects the proposed revision and evidence. Repairs reopen affected checks and findings.

**Code slice review.** Review each new or changed code slice before dependent work builds on it. Keep the slice the smallest coherent, testable unit and group its related edits. Prepare evidence with the repository command, local tests and dry runs as needed. Both reviews below are mandatory for code, in this order and with the named reviewers, unless an authorized human explicitly approves a scoped exception under the execution rules:

1. Run CodeRabbit on the proposed revision. Verify each finding, fix confirmed problems, rerun affected checks and rerun CodeRabbit on the changed scope.
2. Request the final review of the repaired revision from Claude Opus 5.5 in a fresh session that did not write the slice. Ask for only exact additions, deletions or refinements with file and line anchors, or a short statement that none are needed.
3. Apply confirmed Opus fixes and rerun affected checks. If those fixes require CodeRabbit to recheck the affected scope, request another Opus review of the rechecked revision, so Opus always gives the last review. Record both reviews against the final revision.

Hold dependent implementation, deployment, merge or handoff until CodeRabbit reviews first, fresh Claude Opus 5.5 reviews last, confirmed findings are fixed and affected rechecks pass. If either reviewer is unavailable, mark that review step Blocked with the reason. Unrelated work may continue. To skip, substitute, reorder or proceed before either required review, obtain the scoped human exception described in the execution rules before taking the dependent action. This exception applies only to the review gate for the action explicitly named, including at merge or handoff. Record each review actually performed. An outstanding review remains outstanding. A completed fresh Opus review satisfies the independent code review above. Merge authority, deployment authority and human acceptance remain separate.

**Pull requests and merge.** Work on a branch scoped to one story slice or one documentation change, and keep unrelated edits out. Change the default branch through a pull request unless authority already given permits a direct push, and record that source. Open the pull request as a draft while the writer's checks are incomplete. Record the exact revision for every check and review; a local check or CodeRabbit CLI review counts for the pull request only when it records the same revision as the PR head. If CodeRabbit runs through its GitHub App, mark the pull request ready for review before step 1 of the code slice review, because automatic reviewers may skip drafts; marking it ready does not grant merge permission. A push after a result makes that result historical for the changed scope, so rerun the affected checks and reviews on the new head. Keep technical evidence (the checks and reviews recorded against the final head), merge authority and business acceptance as separate records, because none of them implies another. Merge only with authority already given for that repository and branch, and record its source. Before merging code, complete the code slice review or verify a scoped human exception explicitly permitting merge with the specified review deviation. Merge also requires separate authority for the repository and branch. For other changes, if that authority allows merging while evidence or acceptance is pending, list each pending item in the pull request and the story, and do not mark the affected steps Complete. Merging is not acceptance, and acceptance does not authorize a merge or deployment. Scale checks to the change: a change that alters no executable code follows the documentation row in [Code quality checks](../CODE-QUALITY.md) instead of the code slice review. A Salesforce change applies the code slice review to its code, runs the repository's tests and authorized validation against the target environment, and treats deployment as a separate authorized action. For optional repository settings, see the same guide.

Put applicable code checks behind a repository-owned command that works locally and in CI. The linked execution record identifies the check, executor and result. The story links the observed result to the relevant criterion. For examples and an optional Python workflow, see [Code quality checks](../CODE-QUALITY.md).
